# 通用预训练 ViLT：检查小样本检索能力

入口：[通用预训练ViLT对照.py](通用预训练ViLT对照.py)。这一步使用 [dandelin/vilt-b32-mlm-itm](https://huggingface.co/dandelin/vilt-b32-mlm-itm) 的公开权重。它在 GCC、SBU、COCO、VG 上完成 MLM 和 ITM 预训练，**没有使用 Flickr30k 检索微调权重**。本地权重约 543 MB，位置是 `小型复现/pretrained/vilt-mlm-itm/`。

在 `多模态` 文件夹运行：

```powershell
py -3.13 小型复现/通用预训练ViLT对照.py
```

脚本逐行写有中文注释，与 [预训练ViLT小微调.py](预训练ViLT小微调.py) 共用图片读取和检索评估函数。要理解它，先按下面的顺序读。

## 一、为什么要复制 ITM 的一行权重？

通用预训练模型的 ITM 头负责判断一对图文是否匹配，输出两个数字：第 0 个是“不匹配”，第 1 个是“匹配”。检索要给每对图文一个分数，所以取“匹配”那一行作为 `rank_output` 的初始权重。原版 ViLT 检索任务也这样初始化，见本地 [vilt_module.py](../ViLT/vilt/modules/vilt_module.py) 中 `self.rank_output.weight.data = self.itm_score.fc.weight.data[1:, :]`。

`state["itm_score.fc.weight"]` 的形状是 `[2, 768]`：两类、每类 768 个特征权重。`[1:2]` 只取第二行，仍保留二维形状 `[1, 768]`，恰好能填入只输出一个分数的线性检索头。如果只写 `[1]`，结果是 `[768]`，少一维。偏置也用 `[1:2]` 从 `[2]` 变成 `[1]`。

脚本检查这两个键确实存在，并检查权重维度。若模型格式变化，它会直接报错；这样不会把一个随机初始化的检索头误说成预训练模型的效果。

当前 Transformers 在加载时会提示 `rank_output` 缺失，因为原文件保存的是 `itm_score`，并没有同名的检索头。这是任务头名称不同造成的提示；紧接着 `load_base_model()` 会从已训练的 `itm_score.fc` 拷贝对应权重。脚本已实际检查到原权重形状是 `[2,768]`。

## 二、训练和验证各做什么？

1. `evaluate()` 对每张验证图片比较一条正确描述和一条错配描述，得到二选一排序正确率。
2. `evaluate_gallery()` 为 16 张验证图片和 16 条描述全部打分，形成 `[16,16]` 矩阵。行最大值对应图找文，列最大值对应文找图；正确位置在对角线上。
3. `model.vilt.requires_grad_(False)` 冻住已预训练骨干，只训练小检索头。`F.softplus(negative-positive)` 希望正配对分数高于负配对。
4. 微调后重新跑这两种验证，只保存检索头和 JSON 指标；原大权重仍需留在本地，加载检索头时才有意义。

## 三、如何理解结果？

本机使用 64 张训练图、16 张验证图、只训练检索头一轮，得到：

| 指标 | 微调前 | 微调一轮后 |
|---|---:|---:|
| 一条正确描述与一条错配描述排序 | 100% | 100% |
| 16 选 1 图找文 R@1 | 100% | 100% |
| 16 选 1 文找图 R@1 | 94% | 94% |

检索头的平均正负分差从 9.55 变为 9.94，但 R@1 没有改善；这说明这 64 张训练图并未在该验证集上带来可观察的排名收益。数值保存在 `checkpoints/vilt_base_metrics.json`。

这一步比 Flickr30k 专门微调权重更适合观察“通用预训练能迁移多少”，但也**不能自动证明图片从未进入任何预训练数据**。GCC、SBU 等网络图文来源与 Flickr8k 的图片重叠情况尚未逐张核查。这里仅有 16 张验证图，每图只取第一条描述，R@1 会有很大波动。请把结果视为代码与训练流程的教学实验，不把它写成论文级基准。

与 [Flickr30k 检索权重实验](预训练ViLT说明.md) 放在一起看时，也要记住两个权重经历了不同的训练阶段：后者直接做过 Flickr30k 检索任务，且 Flickr30k 与 Flickr8k 的图片可能重叠。
